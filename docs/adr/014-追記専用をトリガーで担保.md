# 014: 追記専用をSQLiteトリガーで担保

- Status: Accepted
- Date: 2026-09-20
- Related: CLAUDE.md ルール1、要件F4-1、基本設計3.5・7章

## Context
基本設計は「`repo.py` は INSERT しか公開しない」ことで追記専用を担保していた。これはアプリ層の規約で、`sqlite3` CLI や別スクリプトからの UPDATE/DELETE、実装者の誤りを防げない。テストも「UPDATE試行で例外」を要求しているが、repo に関数が無いだけでは例外は出ない。

## Decision
- `schema.sql` で凍結対象テーブル（`events` `bundles` `judgments` `answers` `heartbeat` `ledger` `question_versions` `state_versions` `my_calls`）に `BEFORE UPDATE` と `BEFORE DELETE` のトリガーを作り、`RAISE(ABORT, 'append-only: <table>')` する
- `repo.py` は INSERT 系のみ公開（従来通り）。読み取りは `queries.py` に分離
- テストは (a) トリガーにより UPDATE/DELETE が `sqlite3.IntegrityError` になること、(b) `repo` モジュールの公開名に `update` `delete` を含むものが無いこと、の両方を確認する
- 採点系テーブル（`prices` `outcomes` `paper_trades`）は再計算があり得るため追記専用にしない。ただし再計算は新しい `scored_at` の行を追加する形とし、UPDATE は使わない（規約。トリガーは置かない）

## Alternatives
- repo 規約のみ：DB層の保証がない
- 書き込み専用ユーザー：SQLite にはユーザー権限がない
- 別ファイルへの WORM 書き出し：SQLite の一貫性と両立しにくい。日次の `ledger` ハッシュ連鎖で改ざん検知を補う

## Consequences
- 訂正が必要なときは新しい行を追加し、`supersedes_id` 等で旧行を参照する（CLAUDE.md ルール1）
- マイグレーションでテーブル定義を変えるときは、トリガーを一時的に落とす必要がある。`db.migrate()` は前進のみとし、既存行の書き換えを伴うマイグレーションは禁止
