# 026: 切り詰めの予算は送信する JSON の文字数で測り、章の抜粋は別項目に置く

- Status: Accepted
- Date: 2026-09-20
- Related: 要件 F2-4、基本設計3.3、詳細設計 05-state構築 4.4・4.5、ADR 020

## Context
要件 F2-4 と基本設計3.3 は「本文が4万字を超えたら切り詰め」「報告書型は目次から『原因・評価・結論』章の冒頭を追加」とだけ書いていた。実装に落とすと3点が曖昧だった。

1. 4万字は何の長さか。本文の合計か、送る JSON 全体か。Jev の上限（5万〜5.5万字）は入力全体に効く
2. `json.dumps(..., ensure_ascii=False)` でも `"` と改行はエスケープされるので、本文を N 文字削っても JSON は N 文字縮まない。1回の引き算では上限を超えたままになることがある
3. 「章の冒頭を先頭に追加」は `primary.body` を書き換えるので、原文と抜粋の区別が付かなくなる

加えて、基本設計の「目次に頁番号付き章立て」という報告書型の判定は、実物（`tests/fixtures/9502_chubu_report_full.txt`、283,113字）では成立しない。本文に「目次」の語が無く、目次らしき行（ドットリーダー＋頁番号）は123行ある。本文の章見出しは `第6 原因分析` のように**第と数字の間に空白が無い**のが特徴で、`第 1 回ヘルプライン通報` `第 624 回適合性審査会合` `第一原子力発電所` とはその1点で見分けられる。

## Decision
- 予算は `len(json.dumps(state, ensure_ascii=False))`＝**実際に送る文字列の長さ**に対して適用する。`judge.max_state_chars`（40,000）はこの値の上限
- 切り詰めは「測る→削る→測り直す」ループ（最大5回）。収束しなければ `JevfwdError` で止める（無限ループにしない）
- 順序は ①secondary は最大2件だけ全文（要件 F2-4）②超えたら secondary の本文を rank の大きい順に1件ずつ表題のみへ ③報告書型なら章の抜粋を作る ④primary を先頭優先で切る
- 報告書型の判定は見出し行の形（`^第[0-9０-９][ 　]\S` の短い行）の数、またはドットリーダー行の数
- 章のキーワードは `原因 / 評価 / 結論 / 結語 / 再発防止 / 提言`（要件の「結論」は実物では「結語」、「再発防止」は「再発防止策の提言」）
- 抜粋は `primary.body` に混ぜず `primary.excerpts: [{heading, text}]` に置く（`state.v2.schema.json`）
- 見出しの正規表現とキーワードは `state/truncate.py` の定数（根拠付き。00-共通規約 12章）。**変更したら state の版を上げる**（判定に入る文字列が変わるため）。`state_completeness.rules.truncate_rev` に規則の改訂日を残す

## Alternatives
- 本文合計で数える：外枠・表題・直近開示一覧のぶんを見落とし、上限を超えるか、逆に削りすぎる
- 章のキーワードを `filters.vN.yaml` に置く：版の凍結手順（ADR 020）が要るが、これは業務ルールではなくテキスト抽出のヒューリスティック。state 版に紐づける方が意味が合う
- 抜粋を `body` の先頭に足す（基本設計のまま）：原文との区別が付かず、切り詰めの検証ができない

## Consequences
- `bundles.state_json` は**生保存**（`canonical` でキー順を並べ替えない）。並べ替えると送った文字列と保存が食い違い、`state_chars` が合わなくなる（00-共通規約 5章に追記）
- 抜粋は最大4章 × 2,000字 = 8,000字を予算から使う
- 切り詰め規則の改訂は state 版 v3 と件数リセットを伴う（`docs/事前宣言.md` の「変更の扱い」）
