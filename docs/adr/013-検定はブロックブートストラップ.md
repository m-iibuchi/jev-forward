# 013: 関門1の検定は日別ブロック・ブートストラップ

- Status: Accepted
- Date: 2026-09-20
- Related: 要件3章「判定基準」、`docs/事前宣言.md`、基本設計3.8

## Context
要件v2は「3ベースラインを p<0.05 で上回る」としていたが検定方法を指定していなかった。主検証の600件は独立ではない：同日エントリーの件は20営業日の地合いを共有し、隣接日のエントリーは期間の大半が重なる。件を独立とみなす t 検定は p 値を実際より小さく出し、関門1を甘くする。方法を後から選ぶと「通りやすい方法を選んだ」疑いが残る。

## Decision
- **主検証の検定**：エントリー日を1ブロックとする日別ブロック・ブートストラップ
  1. 主検証の各件について超過リターン（コスト控除後、対TOPIX）を求める
  2. 各ベースライン（ランダム・TOPIX・SUEのみ）について、同じエントリー日ごとの対応する超過リターンを求める
  3. エントリー日をブロックとして復元抽出（ブロック数＝元の営業日数）し、Jev群とベースライン群の平均差を計算。これを **10,000回** 繰り返す
  4. 差の分布の **両側95%区間の下限が 0 を上回る** ならそのベースラインに有意に勝つ。3ベースライン全てで成立すれば関門1通過
  5. 乱数 seed は事前宣言に固定値を記載し、`outcomes` の集計時にも記録する
- **感度分析**：ブロックを ISO 週に広げて同じ手順。結論が変わる場合はレポートに両方を載せるが、通過判定は日別ブロックで行う
- **探索**：保有銘柄等加重のポートフォリオ日次リターンとベースラインの日次差の t 検定。論文との比較用。通過判定には使わない
- 単純な Welch の t 検定は採用しない

## Alternatives
- Welch の t 検定：実装は最も簡単だが依存を無視し、関門が甘くなる
- ポートフォリオ日次リターンのみ：サンプル数が営業日数（4週間で約20）になり、600件集めても検出力が上がらない。「有意差なし」が優位性なしか検出力不足か区別できない

## Consequences
- 実装は標準ライブラリ（`random.Random(seed)`）と数十行で済む。numpy 不要
- 3ベースラインすべてに勝つ AND 条件は多重比較で甘くなる方向ではないため補正しない。探索の結果は主検証の結論に使わない
- 期待される検出可能な差は、依存を考慮すると平均超過リターン 2〜3%程度。コスト控除後にこの差が出るかが関門1の実質
