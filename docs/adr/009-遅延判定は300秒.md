# 009: 遅延判定の閾値を300秒にし、取得遅れは別列に記録

- Status: Accepted
- Date: 2026-09-20
- Related: 要件F4-3、3章「運用ルール3」、基本設計3.1・3.2・3.4

## Context
要件v2は「公表から60秒超の判定は遅延フラグを立て主分析から除外」としていた。一方、基本設計は取得周期60秒、束ね猶予120秒（同時刻の後続開示を待つ）としており、最短でも公表から120〜180秒後に判定が始まる。設計通りに動かすと全件が delayed=1 になり、主分析の対象が空になる。

遅延フラグの目的は2つ：(a) 高負荷時に判定が遅れた件を識別する、(b) 公表から判定までの遅れが相場と相関していないか事後検証する。60秒という値は Playground の応答時間（最大762ms）から置いた仮の値で、束ね猶予を考慮していなかった。

## Decision
- `judgments.delayed` は「公表時刻 → Jev応答時刻」が **300秒超** のとき 1
- 公表時刻 → PDF受信時刻の遅れを `events.fetch_lag_sec` に、PDF受信 → Jev応答の遅れを `judgments.process_lag_sec` に別途記録する
- 閾値 300秒は `config/settings.yaml` の `judge.delayed_threshold_sec` から読む。変更は版として記録

## Alternatives
- 起点を受信時刻に変える：システム内部の遅れだけを測ることになり、取得層の遅れ（TDnet側の反映遅れ含む）が主分析に混入する。(b) の目的を果たせない
- 束ね猶予を30秒に短縮し取得周期も30秒に：TDnetへのアクセス回数が倍になり利用条件の確認が必要。同時刻開示の後続を取り逃がすリスクも増える

## Consequences
- 通常運転では delayed=0 が期待値。delayed=1 が続くのは負荷か障害の兆候として heartbeat で監視する
- 事後検証は `fetch_lag_sec` と `process_lag_sec` を使って遅れの内訳を分析できる
- 要件F4-3 と基本設計3.4 を改訂
