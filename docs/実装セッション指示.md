セッションの指示は `docs/detailed/0X-*.md`（契約＋受入テスト）を参照する形にしてあり、完了条件はそのファイルの受入テスト ID で決める。

## 共通の前置き（全セッションで最初に貼る）

```
このリポジトリは、日本株の適時開示を Jev（TypeSafe AI）で判定して凍結記録し、後から採点するフォワードテスト基盤です。

読む順：
1. CLAUDE.md（絶対ルール。特に「凍結ログは追記専用」「版ファイルは変更しない」「過去データで検証しない」）
2. docs/detailed/README.md（章構成、テスト ID の規約、写経の手順）
3. このセッションで指定する docs/detailed/0X-*.md
要件定義書・基本設計書は、指定した詳細設計の「関連」に挙がっている章だけ読めば足ります。全部は読まなくてよい。

進め方（docs/detailed/README.md「写経の手順」）：
1. 対象ファイルの 1〜6 章を読む
2. 8 章の受入テスト表を、上から順に tests/test_*.py へ写す。テスト関数名は表のとおり、docstring の 1 行目に ID（例 """T01-07: UPDATE は 9 テーブルすべてで IntegrityError"""）。この時点では全部 fail する
3. 7 章の擬似コードに沿って実装し、テストを通す
4. 表と食い違う判断が要ったら、コードだけ直さない。まず docs/tasks/NNN-*.md に起票し（一覧 docs/tasks/README.md も更新）、詳細設計を直してからコードを直す。設計判断になるものは docs/adr/ にも残す
5. 表に無いテストを足すのは自由。表のテストを削る・弱めるのは詳細設計を先に直してから

環境（すべて Docker コンテナ内。ホストの Python・venv・pip は使わない）：
- deploy/Dockerfile の dev ターゲット（python:3.11-slim、pip install -e .[dev]）と deploy/docker-compose.yml の dev サービス（リポジトリを /app に bind mount。data/ も同じ mount の中）を使う
- テスト：docker compose -f deploy/docker-compose.yml run --rm dev pytest
- CLI：docker compose -f deploy/docker-compose.yml run --rm dev jevfwd --help
- ホストで python や pip を実行する手順を書かない。コンテナ内の SQLite は 3.40 だが、00-共通規約 10 章の「使わない構文」（RETURNING / STRICT / ->> / json_* / INSERT OR REPLACE 等）は T00-13 が grep で守る
- 外部ネットワークに接続するコード（TDnet、TypeSafe、J-Quants、ntfy）はセッション 2・4 以降。それまでは書かない

守ること：
- config/questions.v1.json, v2.json、config/*.v*.yaml は作成後に変更しない（SHA-256 のテストが検知する）
- src/jevfwd/store/repo.py は INSERT 系だけを公開する。UPDATE / DELETE を書かない
- 秘密（TYPESAFE_API_KEY, JQUANTS_REFRESH_TOKEN, NTFY_TOPIC）はコードにもログにも出さない
- 時刻は UTC で保存。判定・束ねの関数は now を引数で受ける（datetime.now() を業務関数の中で呼ばない）
- scripts/pdf2txt.py と scripts/make_state.py は検証用として残す（動かなくなってもよいが削除しない）

終わったら、次を箇条書きで報告してください：
- 作ったファイル
- 通ったテスト ID の範囲（例 T00-01〜19、T01-01〜27）と pytest の結果行
- 起票した task の番号と、詳細設計を直した箇所
- 次のセッションに渡す事項（未決、気付いた矛盾）
```
