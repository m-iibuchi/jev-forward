## 1. 全体構成

```
┌──────────────── VPS (Docker, 24h) ─────────────────┐
│  fetcher ──▶ bundler ──▶ state_builder ──▶ judge   │
│     │            │             │              │     │
│     ▼            ▼             ▼              ▼     │
│  raw/pdf     SQLite (append-only) ◀───────────┘     │
│                  │                                   │
│  heartbeat ──▶ monitor ──▶ notifier (ntfy)          │
│  digest (18:30 / 07:30 JST) ──▶ notifier            │
│  market_cache (06:30 JST) ◀── J-Quants              │
└──────────────┬──────────────────────────────────────┘
               │ 日次 rsync (SQLite + raw/pdf)
               ▼
┌──── NAS (DS220+) ────┐      ┌──── ローカルPC ────┐
│  backup/YYYY-MM-DD/  │ ───▶ │ scorer (J-Quants)  │
└──────────────────────┘      │ paper_trader       │
                              │ report / calib     │
                              └────────────────────┘
```

プロセスは5つ。すべて同一コンテナ内で `supervisord` または個別の `systemd` サービスとして動かす。周期・時刻は `config/settings.yaml` から読む。

| プロセス | 周期 | 責務 |
|---|---|---|
| `fetcher` | 60秒 | TDnet一覧の差分取得、PDF取得・テキスト化、events書き込み |
| `judge_worker` | キュー駆動 | 束ね確定→state構築→Jev判定→judgments/answers書き込み |
| `heartbeat` | 60秒 | 生存ログ、各キューの滞留数、エラー率、ディスク使用率をheartbeatに書く。異常は通知 |
| `digest` | 平日 18:30 JST（速報便）と 07:30 JST（確定便） | エントリー候補を通知（ADR 010） |
| `market_cache` | 平日 06:30 JST | J-Quants から前営業日の日足・銘柄一覧・TOPIX を取得し `prices` `listed_master` に追記（ADR 017）。段階1では無効化可 |

採点（`scorer`）と模擬執行（`paper_trader`）はローカルPCで日次バッチ。J-Quants Lightは前営業日までの日足なので、採点は1営業日遅れで進む。

## 3. 処理フロー

### 3.1 取得（fetcher、60秒周期）

```
loop:
  list = TDnet一覧を取得（当日ページ、必要なら前日分も）
  for row in list:
    key = (公表時刻, コード, 表題)
    if key in seen: continue
    pdf = ダウンロード（失敗時は3回リトライ、失敗なら pdf_status='failed' で登録し表題のみで進む）
    sha = SHA-256(pdf)
    if sha in events.pdf_sha256: continue          # 真の重複
    text = PyMuPDFでテキスト化（scan_suspect判定）
    xbrl = あれば数値抽出
    events.insert(...received_at=now_utc, fetch_lag_sec=now_utc - published_at)
    bundler.enqueue(event_id)
  heartbeat.tick('fetcher', ok=..., n_new=...)
```

- 一覧の取得方法は段階0で確定（要件10章）。実装は `tdnet_list.py` に閉じ込め、差し替え可能にする
- PDF取得失敗でも一覧が取れていれば `events` に登録し、表題のみで暫定判定する（Playground #17で方向は表題で出ることを確認）

### 3.2 束ね（bundler）

```
入力: 新規event
1. 同一コードで公表時刻±5分のeventsを集める（bundle候補）
2. 猶予: 最初のeventから120秒待ってから確定（同時刻の後続を待つ）
3. 除外判定（filters.yaml、ADR 019）。除外は判定しない:
     - コード/接頭辞でETF・REIT・投資法人・ETN → skip_reason='excluded_instrument'
     - 整理・監理銘柄マスタ → 'excluded_supervised'
     - 上場後60日未満 → 'excluded_new_listing'
     - 除外表題パターン（約款変更、ETF分配金、日々の開示事項）→ 'excluded_title'
   重要度低下パターン（事業計画及び成長可能性、CG報告書改定）は判定するが flags_json に 'low_priority:<種別>' を付ける
4. TOB例外（ADR 003）:
     表題に「公開買付」「ＭＢＯ」「MBO」「株式交換」を含むeventがあれば、
     そのeventを単独bundle（bundle_role='tob_primary'）にし、同時刻の無配・特別損失等は bundle_role='tob_attached' で別bundle（判定はするが主検証から除外）
5. 連番表題（ADR 016）: 連番部分（（１／３）等、filters.yaml の sequence_patterns）を除いた表題が一致する events を
   1つの「論理開示」として logical_docs_json にまとめる。events は1PDF=1行のまま。本文の連結は state 構築時
6. 主開示の選定（優先順、論理開示単位）: 業績予想の修正 > 不祥事・処分・意見不表明 > 資本政策 > 決算短信 > 訂正・事務
7. session の判定（ADR 011）: anchor_published_at を JST に変換し、15:00:00 以降 → 'after_close'、
   翌営業日 08:00:00〜08:59:59 → 'pre_open'、09:00:00〜14:59:59 → 'intraday'。休日は 'after_close'
8. bundles.insert(...), judge_worker.enqueue(bundle_id)
```

### 3.3 state構築（state_builder）

```json
{
  "issuer": {"company": "株式会社ほぼ日", "code": "3560", "market": "東証グロース", "role": "発行者"},
  "published_at": "2026-09-17T17:30:00+09:00",
  "market_context": {
    "prev_close": 4530, "market_cap_jpy": 11000000000,
    "return_20d_vs_topix": 0.021, "avg_turnover_20d_jpy": 45000000
  },
  "forecast_context": {"prior_forecast": {...}, "prev_year_actual": {...}},
  "recent_disclosures_30d": ["2026-08-xx 〇〇に関するお知らせ", ...],
  "same_time_disclosures": ["連結決算への移行に伴う…", "決算期の変更…", "定款の一部変更…"],
  "primary": {"title": "業績予想の修正に関するお知らせ", "body": "..."},
  "secondary": [{"title": "...", "body": "..."}, {"title": "...", "body": "..."}],
  "other_titles": ["..."],
  "state_version": "v2"
}
```

切り詰め（`truncate.py`）：
1. 合計が4万字以内ならそのまま
2. 超えたら secondary の本文を表題のみに落とす → まだ超えたら primary を先頭優先で切る
3. primary が報告書型（目次に頁番号付き章立てがある）なら、「原因」「評価」「結論」「再発防止」の見出しを検索し、その章の冒頭2,000字を先頭に追加してから切る

`market_context` の直前終値・時価総額・20日リターン・平均売買代金は、`market_cache` プロセス（ADR 017）が J-Quants から日次で `prices` `listed_master` に入れた前営業日データを `queries.py` 経由で読む。取れない場合は null で進め、`state_completeness_json` に欠損項目を記録する。連番表題の本文は `logical_docs_json` の順に連結してから切り詰める。state の書式は `docs/contracts/state.v2.schema.json` を正とし、`freeze-state --version v2` で `state_versions` に凍結する。

### 3.4 判定（judge_worker）

```
qv = question_versions から 'v2' を取得（未凍結なら JudgeError。ADR 020）
questions = render(qv, company, code)                    # 主語固定文に company/code を埋める
purpose = 'provisional' if bundle の本文が表題のみ else 'full'
for model in ['jev-latest', 'jev-preview']:
  t0 = now
  resp = POST /v1/systemone {model, state, questions}   # timeout 10s, retry 3 (指数バックオフ)
  t1 = now
  judgments.insert(bundle_id, model, purpose, question_version, state_version,
                   request_json, response_json, requested_at=t0, responded_at=t1,
                   latency_ms, error_type, input_chars,
                   process_lag_sec = t1 - received_at,
                   delayed = (t1 - published_at > settings.judge.delayed_threshold_sec))   # 既定 300
  for q in resp.answers: answers.insert(...)
```

- エラー（`max_tokens_exceeded` 等）も必ず judgments に行を残す（欠損の相関分析のため）
- 生レスポンスから版情報らしき項目（`model_version`, `id` 等）があれば `model_version` 列に抽出。なければ null。項目名は task 002 の採取結果で確定
- 表題のみで暫定判定した bundle に PDF が後から到着したら、同じ bundle に `purpose='full'` の行を追加する（ADR 015）
- 遅延の閾値は 300 秒（ADR 009）。60 秒では束ね猶予（120 秒）と取得周期（60 秒）で全件が遅延になる

### 3.5 凍結ログ

- SQLite、WALモード。アプリ層で UPDATE/DELETE を発行しない（`repo.py` はINSERTのみ公開、読み取りは `queries.py`）
- DB 層でも凍結テーブルに `BEFORE UPDATE` / `BEFORE DELETE` トリガーを置き `RAISE(ABORT)` する（ADR 014）。テストはトリガーで例外になることを確認する
- 採点・キャッシュ系（`prices` `listed_master` `outcomes` `paper_trades`）はトリガーを置かないが、再計算は新しい行を追加する（`scored_at` / `source_version` で世代を区別）。UPDATE は規約で禁止
- 日次で `PRAGMA integrity_check` と、当日追加行のハッシュ連鎖（前日ハッシュ＋当日行）を `ledger` に記録

### 3.6 監視・通知

- `heartbeat` は60秒ごとに1行。`monitor` は直近3行が欠けたら ntfy に警告
- 日次コスト（入力トークン概算×単価）が閾値を超えたら新規判定を停止
- 週次（土曜）：固定10件（tests/fixtures 由来の state を `bundle_role='fixture'` の bundle として登録済み）を `purpose='recheck'` で再判定し、前回との impact 平均差 > 0.1 で「版入れ替わり疑い」を通知（ADR 015）
- ディスク使用率 80% 超で通知。原本PDFは NAS 転送確認後 30 日で削除（ADR 018）

### 3.7 ダイジェスト（18:30 速報便 / 07:30 確定便、ADR 010）

対象は `session IN ('after_close','pre_open')`、`bundle_role='normal'`、`flags_json` に low_priority を含まない bundles のうち、`entry_rules.yaml` の条件を満たすもの（direction up ≥ 0.8、confidence ≥ 0.6、流動性・時価総額・事前リターン条件）。判定は `purpose='full'` を優先し、無ければ `provisional` を「暫定」と表示。

- **18:30 便**：当日 15:00 以降〜18:30 の候補。予習用
- **07:30 便**：前営業日 15:00 以降〜当日 07:30 の候補すべて（18:30 便の再掲を含む）。注文の最終判断はこの便
- 候補が 1 日の新規上限（3）を超える場合、up 確率 × impact の降順で上位 3 件を注文案、残りは「候補外」として同じ通知に列挙
- 各行：コード、社名、表題、up確率、impact、surprise、想定注文（翌朝寄成、数量＝資金5%÷直前終値）。返信リンクで `my_calls` に「買う／見送る」を記録（07:30 便に対して）
- 営業日判定は task 011 のカレンダーを使う

### 3.8 採点（scorer、ローカル、日次）

```
for bundle in 未採点 and 翌営業日の日足が到着済み:
  entry = 翌営業日の始値（寄らず=特別気配ならNULL、探索用に「当日最初の約定値」も記録）
  for horizon in [1(寄→引), 5, 20, 60]:
    exit = horizon営業日後の終値
    ret = exit/entry - 1 - cost; topix_ret = 同期間のTOPIX
    outcomes.insert(bundle_id, horizon, entry, exit, ret, ret - topix_ret, ...)
overlap: 銘柄ごとに entry_date 昇順、直前採用件の exit_date 以前なら overlap_excluded=1（要件3章「1件の定義」）
baselines: 同日の引け後開示銘柄（主検証と同じ除外・規模・流動性条件）からのランダム抽出（seed 固定、outcomes に記録）、TOPIX、SUE上位（営業利益修正率、定義は task 005）
stats: 日別ブロック・ブートストラップ 10,000 回で3ベースラインとの平均差の両側95%区間（ADR 013）。週ブロックを感度分析、ポートフォリオ日次 t 検定を探索
calibration: up確率のビン別的中率、impactクラスタ別の平均|超過リターン|
features: ギャップ率、出来高倍率、事前20日リターン、同日発表件数、時価総額、Jev各出力
```

主検証の母集団：`bundle_role='normal' AND session IN ('after_close','pre_open') AND purpose='full' AND model='jev-latest' AND delayed=0 AND error_type IS NULL AND overlap_excluded=0` かつ entry_rules の条件。

### 3.9 模擬執行（paper_trader）

`executor` インターフェース：`place(order) -> fill`、`positions()`、`close(position, reason)`。実装は `PaperExecutor`（始値約定、コスト控除）、`ManualExecutor`（ダイジェストの注文案を出し、約定は手入力）、将来 `TachibanaExecutor`。
出口は `rules.py`：`time_exit(20)`, `stop_loss(-0.08)`, `thesis_broken(後続の悪材料開示)`, 探索用 `day1_fade`（記録のみ）。

## 4. データモデル（SQLite DDL要約）

正式な DDL は `docs/detailed/01-凍結ログ.md` → `src/jevfwd/store/schema.sql`。ここは要約。2026-09-20 詳細設計 01 での確定事項（要約には反映していない）：全凍結テーブルに明示の `INTEGER PRIMARY KEY`（heartbeat は UNIQUE なし＋index）、`bundles.supersedes_id`、`question_version` `state_version` の外部キー、列挙・時刻書式・コード長の CHECK、`events.source='fixture'`、`ledger` の列追加（ADR 021）、`code` は TDnet 5文字。2026-09-20 の改訂点：`fetch_lag_sec`、`session` `flags_json` `logical_docs_json`、`purpose` `process_lag_sec`、heartbeat の複合PK、`listed_master` `schema_version`、outcomes の `overlap_excluded` `random_seed`、追記専用トリガー。

```sql
CREATE TABLE schema_version (version INTEGER PRIMARY KEY, applied_at TEXT NOT NULL);

CREATE TABLE events (
  event_id INTEGER PRIMARY KEY,
  code TEXT NOT NULL, company TEXT, title TEXT NOT NULL,
  published_at TEXT NOT NULL,          -- UTC ISO8601（TDnet表示の分単位）
  received_at TEXT NOT NULL,
  fetch_lag_sec INTEGER,               -- received_at - published_at（ADR 009）
  pdf_url TEXT, pdf_path TEXT, pdf_sha256 TEXT UNIQUE, pdf_status TEXT,  -- ok/failed/none
  body_text TEXT, body_chars INTEGER, scan_suspect INTEGER,
  xbrl_json TEXT,
  source TEXT NOT NULL DEFAULT 'tdnet'
);
CREATE TABLE bundles (
  bundle_id INTEGER PRIMARY KEY,
  code TEXT NOT NULL, anchor_published_at TEXT NOT NULL,
  session TEXT NOT NULL,               -- after_close / pre_open / intraday（ADR 011）
  primary_event_id INTEGER NOT NULL,
  event_ids_json TEXT NOT NULL,        -- 束ねた全event
  logical_docs_json TEXT NOT NULL,     -- 連番結合後の論理開示 [{title, event_ids}]（ADR 016）
  bundle_role TEXT NOT NULL,           -- normal / tob_primary / tob_attached / excluded / fixture
  skip_reason TEXT,                    -- excluded_* （bundle_role='excluded' のとき）
  flags_json TEXT NOT NULL DEFAULT '[]', -- low_priority:*, truncated, provisional_only, scan_suspect（ADR 019）
  state_json TEXT, state_version TEXT, state_chars INTEGER, state_completeness_json TEXT,
  created_at TEXT NOT NULL
);
CREATE TABLE judgments (
  judgment_id INTEGER PRIMARY KEY,
  bundle_id INTEGER NOT NULL,
  purpose TEXT NOT NULL,               -- full / provisional / recheck（ADR 015）
  model TEXT NOT NULL, model_version TEXT,
  question_version TEXT NOT NULL, state_version TEXT,
  request_json TEXT NOT NULL, response_json TEXT,
  requested_at TEXT NOT NULL, responded_at TEXT, latency_ms INTEGER,
  process_lag_sec INTEGER,             -- responded_at - events.received_at（ADR 009）
  error_type TEXT, input_chars INTEGER,
  delayed INTEGER NOT NULL DEFAULT 0   -- responded_at - published_at > 300s
);
CREATE TABLE answers (
  judgment_id INTEGER NOT NULL, question_id TEXT NOT NULL, qtype TEXT NOT NULL,
  value TEXT, probability REAL, confidence REAL, distribution_json TEXT,
  PRIMARY KEY (judgment_id, question_id)
);
CREATE TABLE heartbeat (
  ts TEXT NOT NULL, process TEXT NOT NULL, ok INTEGER NOT NULL, queue_depth INTEGER, note TEXT,
  PRIMARY KEY (ts, process)            -- 複数プロセスが同分に書く
);
CREATE TABLE ledger (day TEXT PRIMARY KEY, rows_added INTEGER, chain_hash TEXT);
CREATE TABLE question_versions (version TEXT PRIMARY KEY, json TEXT NOT NULL, sha256 TEXT NOT NULL, frozen_at TEXT NOT NULL);
CREATE TABLE state_versions (version TEXT PRIMARY KEY, spec TEXT NOT NULL, sha256 TEXT NOT NULL, frozen_at TEXT NOT NULL);
CREATE TABLE my_calls (bundle_id INTEGER, decision TEXT, decided_at TEXT, PRIMARY KEY (bundle_id, decided_at));

-- 上記の凍結テーブルには BEFORE UPDATE / BEFORE DELETE で RAISE(ABORT) するトリガーを置く（ADR 014）

-- 採点・キャッシュ（トリガーなし。再計算は新行追加、UPDATE は規約で禁止）
CREATE TABLE listed_master (code TEXT, as_of TEXT, company TEXT, market TEXT, sector TEXT, listed_on TEXT, shares_outstanding INTEGER, source_version TEXT, PRIMARY KEY (code, as_of));
CREATE TABLE prices (code TEXT, date TEXT, open REAL, high REAL, low REAL, close REAL, volume INTEGER, turnover REAL, source_version TEXT, PRIMARY KEY (code, date, source_version));
CREATE TABLE outcomes (
  bundle_id INTEGER, horizon TEXT, scored_at TEXT,
  entry_date TEXT, entry_price REAL, exit_date TEXT, exit_price REAL,
  ret REAL, topix_ret REAL, excess_ret REAL, filled INTEGER, cost REAL,
  overlap_excluded INTEGER NOT NULL DEFAULT 0, random_seed INTEGER,
  price_source_version TEXT,
  PRIMARY KEY (bundle_id, horizon, scored_at)
);
CREATE TABLE paper_trades (trade_id INTEGER PRIMARY KEY, bundle_id INTEGER, executor TEXT, side TEXT, qty INTEGER,
  entry_date TEXT, entry_price REAL, exit_date TEXT, exit_price REAL, exit_reason TEXT, pnl REAL, rules_version TEXT);
```

主分析の対象：`bundles.bundle_role='normal' AND bundles.session IN ('after_close','pre_open') AND judgments.purpose='full' AND judgments.model='jev-latest' AND judgments.delayed=0 AND judgments.error_type IS NULL AND outcomes.overlap_excluded=0`。

## 6. 運用・デプロイ

- VPS：Ubuntu LTS、Docker。`docker-compose up -d`。コンテナ内 supervisord で4プロセス。`restart: always`
- 時刻：VPSはNTP同期済みが前提。起動時に `date` と外部時刻の差を確認しログに残す
- バックアップ：`deploy/backup_to_nas.sh` を VPS の cron（毎日 02:00 JST）で実行。`sqlite3 .backup` で一貫スナップショットを取り、NAS へ rsync over SSH（NAS側はポート開放せず、NAS→VPSへのpullでも可）。7日分をローテーション
- 通知：ntfy（トピック名は秘密扱い）。Discord webhookでも可
- ログ：標準出力→Docker logs、7日ローテ
